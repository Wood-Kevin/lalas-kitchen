Cross-platform blockers

Affects both stores

These stop submission regardless of which platform ships first.

No consent flow exists before AdMob requests an ad
Blocker
Every rewarded-ad request fires unconditionally — no Google User Messaging Platform (UMP) integration, no requestConsentInfoUpdate, no region check, anywhere in the codebase. Google’s EU User Consent Policy requires a consent-management flow before requesting ads from EEA/UK users; its absence risks AdMob account action independent of what either app store does at review time.
services/expoGoogleMobileAdsService.ts — RewardedAd.createForAdRequest() called with no RequestOptions, no MobileAds().initialize()/setRequestConfiguration() anywhere in the repo
App icon and splash screen are still Expo’s stock placeholder art
Blocker
Confirmed by opening the actual image files: the launcher icon is the literal default green Android-robot template icon, and the splash screen is a plain gray bullseye on white. Nothing in app.json even references an icon or splash source — there’s no pending real asset waiting to be wired in, this needs real branded art designed from scratch.
android/app/src/main/res/mipmap-xxxhdpi/ic_launcher.webp · android/app/src/main/res/drawable-xxxhdpi/splashscreen_logo.png · app.json has no icon/splash keys at all

iOS: not a gap, a blank slate

iOS App Store

Every item below compounds — none is reachable until the one before it exists.

No ios/ native project exists — never built once, for any reason
Blocker
Confirmed absent. Android has a committed, real, previously-compiling native project that already caught and fixed one real launch crash this session. iOS has nothing to build from yet — the first eas build -p ios (or local prebuild) will be this app’s literal first contact with Xcode, provisioning, and every issue that surfaces only at that point.
No iOS bundle identifier configured
Blocker
app.json has an ios.supportsTablet and ios.infoPlist block, but no ios.bundleIdentifier anywhere. An iOS build cannot start without one.
App Tracking Transparency (ATT) prompt is missing
Blocker
No NSUserTrackingUsageDescription, no expo-tracking-transparency, no call to request tracking authorization. Apple requires the ATT prompt for any app bundling a tracking-capable ad SDK — AdMob qualifies regardless of whether ads end up personalized — and checks for this specifically, both automated and manual, when a known ad SDK is detected in the binary.
No Privacy Manifest (PrivacyInfo.xcprivacy)
Blocker
Apple has rejected App Store Connect uploads missing this since spring 2024 for any binary linking SDKs like AdMob that use “required reason” APIs. Currently latent only because there’s no iOS build to reject yet — it will surface the moment one exists.
No SKAdNetwork identifiers configured
Risk
Google’s iOS AdMob integration guide requires a long list of SKAdNetwork IDs in Info.plist for ad attribution to work correctly. Not present anywhere in app.json.

Android: further along, real gaps remain

Google Play

The native project genuinely builds and a real device crash was already found and fixed this session — but these are still open.

Two storage permissions declared, neither used by app code
Risk
READ_EXTERNAL_STORAGE / WRITE_EXTERNAL_STORAGE traced to a transitive dependency (expo-file-system, pulled in by the expo package itself) — no FileSystem, MediaLibrary, or PermissionsAndroid call exists anywhere in this app’s own code. Broad permissions with no matching feature are exactly what Play’s permissions review flags.
android/app/src/main/AndroidManifest.xml
SYSTEM_ALERT_WINDOW present in the release manifest, not just debug
Risk
Traced to React Native’s own dev-mode overlay, but it’s declared in the main manifest (which release inherits), not scoped to the debug source set. This is the “draw over other apps” permission, associated with overlay-attack malware patterns — Play reviews it with real scrutiny, and it has no legitimate purpose in a shipped build.
Release signing config still points at the committed debug keystore
Risk
Fine if every real build goes through EAS-managed credentials — but that workflow has never been confirmed or dry-run (eas.json’s submit.production is an empty object, no service-account key configured). A local gradlew bundleRelease today would produce a build signed with the public debug key.

What’s never actually been confirmed on real hardware

Both platforms

This project has an unusually thorough verification habit — nearly all of it was run against a headless browser, not a physical device.

Haptics has never fired on a real device
Risk
The Settings toggle correctly persists the preference — that’s all that’s confirmed. expo-haptics is native-only and resolves to a no-op on web, so whether an actual vibration pulse fires has never been checked, on either platform.
The one real human listen to the sound design reported a failure, never re-confirmed
Risk
The first tone pass was described as sounding like “a bright, exciting slot machine” — the opposite of the calm brief this game is built around. Three redesign passes followed, verified only by frequency-analysis math (decay curves, clipping checks) — never by a human ear again.
No rewarded ad has ever been confirmed to actually render on a device
Risk
The request pipeline is proven correct — a real device produced a genuine no-fill response from Google’s ad servers, confirming the App ID and ad unit wiring work. An ad has never been confirmed to actually load and display to a user.
The crash class that already bit this app once was never swept for other instances
Risk
The one real crash this app has had happened before React/JS even initializes — a native ContentProvider failing on process start, invisible to the JS-level ErrorBoundary entirely. It was found and fixed for AdMob specifically. No equivalent check has been run against the other native modules in this app (audio, haptics, gesture handling, storage) — and iOS is a complete unknown here, since it’s never been built at all.

Operational risk, once this is actually live

Post-launch
No remote crash reporting
Risk
The only crash record is local to the device (SaveData.lastCrash, surfaced in Settings) — a crash a real user hits is invisible unless they happen to open Settings and report it. A deliberate, disclosed tradeoff for a small project, worth reconsidering now that this is heading toward a public store listing.
No automated test pipeline
Risk
600+ tests exist and pass locally, but nothing runs them automatically — no CI config anywhere in the repo. Combined with committing straight to master, nothing currently gates a regression from shipping.
Ad SDK deliberately pinned below latest, dropping a consent-relevant API
Risk
react-native-google-mobile-ads is held at 16.0.0 (not the latest 16.4.0) to work around a real Kotlin-toolchain incompatibility. The versions being avoided add setAgeRestrictedTreatment, an API with real Play Store ads-policy relevance depending on how this app’s audience ends up declared at submission.
Store submission credentials have never been configured or dry-run
Risk
eas.json’s submit.production exists but is empty — no Play Console service account, no App Store Connect API key. Not broken, but untested; the first real eas submit will be a first attempt at this too.

The one decision this audit can’t make for you

iOS is not behind Android by a few tasks — it hasn’t started. Every iOS item above compounds on the one before it: a bundle identifier has to exist before a build can run, a build has to succeed before ATT/privacy-manifest work can even be tested, and none of that has ever been attempted once. Android, by contrast, already has a real crash-fix under its belt. Worth deciding explicitly whether this ships Android-first, or whether both platforms wait for iOS to catch up — that changes what “next” means below.

Recommended sequence

If shipping Android first
  1. Wire the Google UMP consent flow
    Blocks ad requests correctly until consent is collected. This gates every other AdMob-adjacent fix below it, so it’s worth doing before anything else — an ad-serving app with no consent flow is the one item here with real account-level consequences, not just a review risk.
  2. Commission and wire real icon & splash art
    Add the icon/splash keys to app.json and replace the Expo default assets in android/app/src/main/res/ — both need to change together, or a future prebuild will just regenerate the placeholders.
  3. Clean up the Android manifest
    Drop the unused storage permissions, scope SYSTEM_ALERT_WINDOW out of the release manifest, and confirm a real EAS-managed signing build (not the local debug keystore) is what actually ships.
  4. Run one real physical-device pass
    Confirm haptics actually fire, do an honest human listen to the three sound cues against the calm brief, and confirm a real rewarded ad genuinely loads and displays — not just that the request pipeline works.
  5. Configure and dry-run eas submit for Android
    Wire the Play Console service account key, then complete the console-side Data Safety form and age-rating questionnaire — both are manual steps with no repo trace, and neither is a code change.
  6. Decide iOS’s timeline separately
    Set the bundle identifier, run the first-ever iOS build, and expect it to surface its own new issues before ATT, the privacy manifest, and SKAdNetwork config can even be tested against something real.
